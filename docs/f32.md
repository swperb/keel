# `f32`

Step 3 of Keel's path to GPUs: IEEE single-precision floats, so real
kernels can be written. Keel proves nothing about float values; it keeps
proving everything else about code that uses them.

## What exists

- The type `f32`, and arrays `[f32]`, `&[f32]`, `&mut [f32]`.
- Literals: `1.5`, `0.25`, `3.0e-7`, `-2.0` (digits, a point, digits, an
  optional exponent; rounded to the nearest f32). A literal must be finite.
- `+ - * /` and `== != < <= > >=` on two f32 values, and unary `-`.
  No `%`, no bitwise operators.
- Explicit conversions, the only way between f32 and integers. f32 never
  meets an integer in one operation (`E-TYPE`).

| builtin | meaning |
|---|---|
| `to_f32(n)` | the f32 nearest the integer `n` (round to nearest even) |
| `to_i64(x)` | `x` rounded toward zero, saturating: values at or beyond ±2^63 give `i64::MAX` / `i64::MIN`, NaN gives 0 |
| `f32_bits(x)` | the IEEE bit pattern of `x`, as an integer in `0..2^32` |

`to_i64` is total on purpose: C's own float-to-integer conversion is
undefined behaviour out of range, and a range proof would need exactly the
float reasoning Keel does not do. Saturation with NaN to 0 is Rust's `as`
rule. Note that 2^63 - 1 is not an f32; the largest finite f32 below 2^63
converts exactly.

Not yet: f32 struct fields, f64, math functions (`sqrt`, `exp`, ...),
float reductions.

## What is proven, and what is not

The verifier treats every f32 value as unknown. Each float operation
(literal, arithmetic, comparison, conversion) yields a fresh value with no
constraints, so no proof can depend on what a float is. Everything around
the floats is still proven as usual:

- array indices, including indices computed from floats, are in bounds:
  `let k = to_i64(x * 10.0);` followed by `if 0 <= k && k < len(xs)` is
  enough, and without the test the index is rejected (`V-BOUNDS`), since
  `k` may be anything;
- `par for` loops over float arrays are race-free (`V-RACE`);
- loops terminate and integer arithmetic does not overflow.

**Specifications may not mention f32 values** (`E-SPEC`): no f32 in
`requires`, `ensures`, invariants, asserts, quantifiers, spec fns or
lemmas, and no specification may call a fn that computes with floats, even
one returning an integer. So nothing about a float can be claimed, and
therefore nothing unsound can be. Arrays of f32 may still appear through
their lengths (`len(xs) == len(ys)`).

Why not more: exact IEEE reasoning in the solver is sound but slow and
brittle beyond small examples, and reasoning about floats as real numbers
is fast but unsound (it "proves" `(a + b) + c == a + (b + c)`). Starting
with no float reasoning is the only option that is both sound and
predictable; exact IEEE reasoning can be added later as an opt-in.

## Run-time semantics

f32 is IEEE 754 binary32 with round-to-nearest-even, on the CPU and the
GPU alike. NaN and infinities are ordinary values: `0.0 / 0.0` is NaN,
`1.0 / 0.0` is infinity, comparisons with NaN are false except `!=`, and
none of this is an error. Subnormals are kept (no flush to zero).

Both backends round every operation separately: the C is compiled with
`-ffp-contract=off` and the PTX uses explicit `.rn` instructions, so
`a * b + c` is never fused into one rounding. The result is that **the CPU
build and the GPU build compute bit-identical floats**. `examples/f32.kl`
and `bench/parfor/logistic.kl` check this on the logistic map, which is
chaotic: a single differently rounded operation would change the result
completely. The one exception is the bit pattern of a NaN (`f32_bits` of a
NaN), which IEEE leaves to the hardware and may differ.

The differential tests also caught a real difference while this was built:
PTX's float-to-i64 conversion turns NaN into `i64::MIN`, not 0, so the GPU
backend tests for NaN explicitly.

## Measured

`bench/parfor/logistic.kl`: 256 steps of the logistic map
`x = (3.9 * x) * (1.0 - x)` for each of 10M slots, then a serial checksum
of the bits. Rust (`rayon_bench logistic`) does the same work and must
print the same checksum, and does: Keel's C, Keel's PTX and Rust compute
bit-identical results. Numbers are in [par-for.md](par-for.md#measured-f32).
